# AGENTS.md

**slag** is a browser party platformer: each round players **pick** a prop from a crate, **place** it in the level, then **run** to the flag (1–8 players, `MAX_PLAYERS`). Levels, props, characters, names and visuals are all procedurally generated from a seed. Movement is a tight precision platformer: walk by default, hold **run** for speed and long jumps, variable jumps, wall slide/jump, coyote time, jump buffering. Use the genre's mechanics. Parody other games, especially with items, but never use their real names, art, characters or level designs (`docs/DESIGN.md` → Parody).

Game design decisions live in [docs/DESIGN.md](docs/DESIGN.md): follow it, and update it in the same commit when a decision changes. [docs/DECISIONS.md](docs/DECISIONS.md) logs every owner decision with its date, status and what it replaced; add the owner's new decisions there too. Open work is in [docs/TODO.md](docs/TODO.md); remove items when they land. UI art direction (palette, type, casing, input prompts) is in [docs/ART.md](docs/ART.md). Folders with their own rules have a nested `AGENTS.md`: `src/sim/`, `src/gen/`, `src/render/`, `src/brain/`, `app/`. Read it before editing there.

## Commands

Package manager is **pnpm** (`packageManager` in package.json). Never use npm or commit a `package-lock.json`. pnpm settings live in `pnpm-workspace.yaml`, not `package.json`. Node 24 (`.nvmrc`, `engines`).

Lint: `oxlint` (type-aware; slag's own rules are a JS plugin, `tools/lint/slag-plugin.mjs`). `.oxlintrc.json` is generated: edit `tools/lint/config.ts`, where each restriction list is written once and a zone's list includes every overlapping earlier zone's (oxlint itself replaces a rule's options per override), then `pnpm lint:config` (`pnpm format` runs it too; `pnpm lint` fails while it's stale). Warnings are real findings, not noise: `pnpm lint` and CI fail on them like errors. Format: `oxfmt` (`.oxfmtrc.json`: 2 spaces, single quotes, 160 columns). Don't add `oxlint-disable` comments to get green; fix the code or change the rule in `tools/lint/config.ts` with a reason. A tool run fails on an option nothing in it read (`argReader`, `tools/lib/server.ts`), so a mistyped flag can't pass silently.

## Definition of done

1. `pnpm check` passes, run **once before committing**. While iterating, run only the test files you touch (`pnpm vitest run tests/x.test.ts`) plus `pnpm check:fast`. Never skip, delete or weaken a test to get there.
2. `pnpm build` passes if you touched `app/`, `next.config.ts`, `package.json`, or what `app/` imports from `src/`.
3. Visual change: you took a screenshot and looked at it (see below). Typechecking says nothing about pixels.
4. Generator change: `pnpm level --stats 50` shows `fallbacks: 0` and no unexplained jump in ms/level or `needBridges`; compare against a run on the parent commit.
5. Behavior change: a test covers it (generator invariants, prop module runtime behavior, physics feel regressions). Test behavior and invariants, not every tunable or weight. Keep tests cheap, because every second is paid on every iteration by every agent; give each test one fixed seed count, a few seeds rather than hundreds. A sweep (every theme × size × gravity, dozens of seeds, seeded fuzz) runs a rotation in `tests/` (each case once, the axes taking turns) and the full product in `tests/stats/`, through one helper in `tests/lib/`. An assertion that needs many seeds to mean anything (a share, a variety count) goes in a file under `tests/stats/` named for what it measures. No skips, and no seed counts that depend on the environment.
6. In your final message, show evidence: the commands you ran with their result, and screenshot paths.

### Verify visually

`pnpm shot` builds a production server (`next build` only if the content of the sources changed since the last build, then `next start`; `SHOT_DEV=1` uses `next dev`). It pauses the real-time loop and advances the sim with `slagDebug.step(n)`, so shots are deterministic. It exits on its own after writing its PNGs, non-zero if the page logged errors or nothing happened for `SHOT_TIMEOUT` seconds (default 180), and never leaves a server running. Open the PNG it prints and inspect it.

- `race --seed S --race saw,laser,launcher --frames 200` (`--race all` = one of every archetype)
- `lobby` | `pick` | `place` with `--seed S --players N` (`lobby --bots N` seats that many bots after them)
- `mobile [--device "iPhone SE landscape"] [--only lobby]`: emulated phone, real multi-touch, fails on a tap target under 44 CSS px, two lobby tap targets that overlap (1–8 players, on its side and upright), or a runner off screen
- `levels --count 9`, `--seeds a,b,c` or `--themes all` → contact sheet `shots/levels.png`
- `cast`: the character cast, lineups at play scale on farm and mine, a close-up, deaths, the lobby, the "is it the homage?" sheet, the silhouette test and a catalog of every kind (`--only catalog`)
- `artqa --theme T` (`--themes all`): every landmark, hazard and decor piece of a theme beside its terrain and three parts, at play scale and 2× (`src/render/AGENTS.md` → Drawing a landmark, hazard or decor piece)
- `props --count 24` (crate cards), `codex [--map castle]` (the `/codex` page: parts, a theme's maps, a landmark and a hazard up close, on a desktop and a phone), `stack` (heads as perches: bucked, slid, knocked and tipped off, as stepped frames)
- Options: `--theme farm`, `--weather rain`, `--noui` (hide HUD), `--noletters` (no impact words), `--nocel` (no cel pass: the Canvas2D compositor), `--size 1280x720`, `--out shots`, `--engine webkit` (WebKit with an iPhone profile is the stand-in for iOS Safari: `mobile --engine webkit`)

Dev URL params (`src/debug.ts`, `src/game-client.ts`): `?seed=abc`, `?theme=farm`, `?bots=2` (seat built-in bots), `?weather=rain` (clear|wind|mist|rain|snow, skips worldgen's gate), `?difficulty=hard` (gentle|medium|hard; `pnpm level` takes `--difficulty` too), `?players=2` (auto-join and start), `?race=saw,laser` or `?race=all`, `?propseed=3`, `?ui=0`, `?zoom=1` (phone camera on desktop; `?zoom=0` off, `?zoom=2.4` a fixed zoom), `?lettering=0` (no impact words), `?debug=1` (dev overlay: frame-time breakdown, counts, level info; ` toggles it in `pnpm dev` or with any `?debug`). In the console, `slagDebug` has `quickStart`, `addBot`, `race`, `addProps`, `give`, `loadLevel`, `phase`, `pause`, `step`, `render`, `hash`, `toys`.

## Git workflow

- Main session: work on `main`. `git pull --rebase origin main`, make small focused commits, and `git push origin main` after every green change. Dev containers are ephemeral, so unpushed work is lost. No feature branches or PRs unless the user asks.
- Subagents in worktrees: run `pnpm install` first, edit only the files your brief assigns, commit to your worktree branch, and **do not push or touch `main`**. Never use bare `git stash` (the stash is shared across worktrees).
  - Before you report done, run `git merge origin/main` into your branch, resolve any conflicts there, and run `pnpm check` on the result, so the orchestrator lands a tree that was already gated.
  - Leave `SNAP_VERSION` and `docs/TODO.md` alone: every branch bumping one integer or editing one list conflicts with every other. Say in your report that the snapshot changed, or which TODO items are done. When `tests/snapshot.test.ts` says the wire shape changed, run `pnpm snap:shape` and commit `src/net/snapshot-shape.json`: that file is how `pnpm land` knows to bump.
  - For before/after numbers, run `pnpm stats:compare <suite>…` rather than extracting the parent commit's tree yourself: it makes and removes its own worktree, shares cached base results with other agents, and is one plain command the guard allows.
  - The worktree guard refuses any command it can't prove stays in your worktree, and each refusal costs a turn. Give `git` a Bash call of its own (no `&&`, pipes, subshells or variables around it) and never `git -C` another worktree. Don't loop over `pnpm shot` with a shell variable: pass a list where the scenario takes one (`levels --seeds a,b`) or make separate calls.
  - The app's task list and wrap-up (`update_plan`, `wrap_up`) belong to the main conversation; a subagent's calls are refused.
- Orchestrators land branches with `pnpm land <branch>…` (`tools/land.ts`): it merges the batch (regenerating `src/net/snapshot-shape.json` when that is the only conflict), bumps `SNAP_VERSION` once if the snapshot changed (its code, the test's field lists, or the shape file), runs the gate once (plus `pnpm build` when the host changed) and pushes. Batch the branches that are ready instead of landing each as it finishes. A conflict stops it with the merge in progress: resolve, commit, run it again with the branches left.
- Orchestrators stay small: hand screenshot review to the `verifier` agent instead of opening PNGs in the coordinating conversation. While agents run, send new requests as messages; stopping the orchestrator's turn stops every background agent with it.
- If you must change a shared contract (`src/sim/props/types.ts`, `src/sim/props/registry.ts`, `src/themes.ts`, `src/sim/types.ts`), keep it additive and call it out in your report.
- Orchestrators define contracts (types, registries) and commit them to `main` before fanning out.
- Commit messages: imperative summary line saying what changed and why it matters.

## Invariants

- **Determinism.** The sim is a pure function of `(seed, per-frame inputs)`; tests run two identical headless matches and compare. In `src/sim`, `src/gen`, `src/game`, `src/themes.ts`, all randomness comes from `Rng` (`src/core/rng.ts`) with sub-streams from `deriveSeed(seed, 'label')`: no `Math.random`, no wall clock, no DOM. Lint enforces this.
- **Layering.** `sim/`, `gen/`, `game/` never import `render/`, `input/`, `audio/`, `ui/`. `render/` reads sim state and never writes it. Lint enforces the imports.
- **Client-only game.** Everything in `src/` runs in the browser; Next.js pages are thin shells (see `app/AGENTS.md`). No React or Next imports in `src/` (lint enforces).
- **Every screen is part of the game.** The main menu, lobby list, lobby, settings, codex, About, 404 and error screens all live in `src/` and are reached from the game's own menus; a URL is just another way in. Move between screens with the `Nav` a screen is given (`nav.go(HOME)`), never `location.assign` or `history.pushState`: lint allows those only in `src/router.ts`. A new screen is a `Route` in `src/routes.ts` and an entry in `SCREENS` in `src/main.ts`, it must be reachable from a menu, and its mount returns an unmount that lets go of everything it took.
- **Frame budget.** Every peer waits on the slowest step, so nothing inside the fixed step may take long. A level the match changes to comes from the worker that builds ahead: anything that can change the level (a rule, a menu action, the next match) must show up in `Match.upcoming()`, or the whole room stalls while the main thread generates it. Per-frame thinking (bots) gets a time budget rather than finishing a plan on the spot.
- **Netcode state** (`docs/NETCODE.md`): sim state is plain, snapshot-friendly data (no closures or class instances holding hidden state, no order-dependent `Map` iteration). Inputs are the only per-frame data that crosses the network.
- **Fairness.** Characters are cosmetic. Every player shares one hitbox and one physics model.
- **Registries over switches.** Extend a subsystem through its registry, not with a new `switch` elsewhere.

## Where things live

- `src/main.ts`: `mountGame(root)`, the one entry point for every host: shows the screen for the URL and moves between screens without a reload (`src/router.ts`, routes in `src/routes.ts`). Screens: `src/ui/screens/` (main menu, lobby list, About, 404, error, the logo), `src/game-client.ts` (lobby and match), `src/codex/main.ts`.
- `src/game-client.ts`: `mountLobby(root, room, nav)`: canvases, input, menus, fixed 60 Hz loop, and the teardown that leaves the room. Each step: input → `Match.step` → `RunWorld.step` (props `build` solids/hazards, then `trace` rays → `stepBody` → hazards/springs/goal → runner contact in `sim/collide.ts` → props `tick`) → events queue → `Renderer.render`.
- `src/sim/`: deterministic simulation (physics, level, reachability, run world, prop modules). `src/gen/`: generators (levels, set pieces, props, theme looks, characters, names). `src/game/`: match state machine (lobby → pick → place → run → score → victory) and `scoring.ts`. `src/net/`: online play (session, transports, signaling client, snapshots). `src/brain/`: bots (senses, brains, the motor that presses their buttons, seats). `src/render/`: Canvas2D layers + WebGL2 post; the HUD is `hud.ts`, with a painter per phase in `hud/`. `src/input/`: keyboard/gamepad/touch → `InputFrame` (bindings in `bindings.ts`). `src/audio/`: procedural SFX and per-theme music. `src/ui/`: the DOM screens (`screens/`), the menus over a game (`menus/`: Settings, Rules, Name), drawn on canvas with the widget kit in `kit/` so they need no DOM, and the touch overlay (`touch/`). Tools press menu controls through `window.slagUi` (`tools/lib/menu.ts`), not selectors. `src/codex/`: the `/codex` catalog of parts and maps.
- `tools/`: `shot.ts` (scenarios in `shot/`), `level.ts`, `online-test.ts`, `perf.ts`, `brand.ts`, `store-test.ts`; `lib/server.ts` builds and boots the production server the browser tools share. `tests/`: vitest, one file per subsystem. `tests/conformance/`: every registered generator entry held to its contract (part of `pnpm test`). `tests/stats/`: distribution and balance suites, one file per measure. `tests/lib/`: the per-seed checks both share.

## Extension points

Every generated kind (landmark, set piece, decor, part, level shape) is a registry entry with its contract declared as data; the pipeline enforces it while generating and `tests/conformance/` checks every registered entry, so a new one needs no new test. The step-by-step guide, with the contract fields, is in `src/gen/AGENTS.md` → Generators, contracts and the conformance suite.

- **Prop module type**: add the variant to `Module` in `src/sim/props/types.ts`; implement `ModuleSim` in `src/sim/props/modules/<type>.ts` and export it from `modules/index.ts`; add art in `src/render/props/modules/<type>.ts` and import it from that `index.ts`; add tests.
- **Player prop archetype**: a recipe in `src/gen/props.ts` (`RECIPES`, typed by archetype, and `ARCHETYPE_WEIGHTS`). Names come from rolled params; what scales goes in the recipe's `sized`.
- **Projectile**: add to `Ammo` and `AMMO` (`src/sim/props/types.ts`); behavior goes in `AMMO_SIM` (`src/sim/props/ammo.ts`), art in `AMMO_ART` (`src/render/props/projectiles.ts`). A launcher style goes in the `launcher` recipe, with art in `src/render/props/modules/launcher.ts`; a style whose object is long or tall gets a frame in `LAUNCHER_FRAMES` (`src/sim/props/launcher-frames.ts`) and its art in `launcher-framed.ts`.
- **Blast shape**: add to `BlastShape` and `BLAST_SHAPES` (`src/sim/props/transform.ts`).
- **Theme**: add the id to `THEME_IDS` and `THEME_LABELS` in `src/themes.ts`, then `tsc` lists every `Record<ThemeId, …>` to fill: `SET_KITS` (its kit of level pieces, `src/gen/level/sets/`: every kind in `KIT_KINDS`), `SET_PIECE_RECIPES`, the look `RECIPES` in `src/gen/theme/presets.ts`, music `STYLES` (with a second arrangement in `arrangements`, balanced with `pnpm music --solo`), `GROUND_TONE`, its codex line in `THEME_NOTES`. The codex's maps pick it up from there. A farm must read as a farm at a glance. Add it to `LATE_THEMES` too, so every existing seed keeps its theme.
- **Set pieces**: per-theme recipes in `src/gen/setpieces/<theme>.ts`; flag one `unique` if no other theme hurts the same way, and give it a `codex` card: it shows up in the codex's maps by itself (see `src/gen/AGENTS.md`).
- **Landmark (stage concept)**: `defineConcept` in `src/gen/stage/<theme>.ts`, listed in `CONCEPTS`, with its contract (`scale`, `footing`, `ways`, `varies`, `names`, `family`) and its `codex.about`: it shows up in the codex's maps by itself.
- **Decor**: a rule in `src/gen/decor/index.ts` (`defineDecor`: themes, top or under, weight, room), art in `src/render/decor.ts`.
- **Terrain look**: a `TerrainKind`, `CapKind` or `PlatformKind` draws through a registry in `src/render/ink-material.ts` and `ink-terrain.ts` (see `src/render/AGENTS.md`).
- **Character kind**: add the id to `CAST`, its sound-alike name (never a respelling of the original's) to `KIND_NAMES` and its own colors to `PAINTS` in `src/gen/character.ts`, its `KindArt` to `KINDS` in `src/render/cast/kinds.ts` (a hand-inked outline, the traits people recognise, a gait, a face, the player's color on the body or a `ring`), and its caption to `READS_AS` in `src/render/cast/sheet.ts`. `pnpm shot cast` → `cast-recognise.png` and `cast-silhouettes.png` must both pass; bump `LOOK_CAST` (`src/ui/profile.ts`). Never a real character's name in code or UI (Junior, Sentry's own robot and an easter egg, is the one exception: `EGGS`). Its entry is `docs/characters/<kind>.md`; the rules are `docs/CHARACTERS.md`.
- **Playstyle mode**: the id in `ModeId` and `MODE_IDS`, and a `ModeDef` in `MODES` (`src/game/modes.ts`): its label; the level it asks for (`profile`: a `builder` by name, `loop`, `bare` to owe no part, `boxes` with the deal table its own boxes hand out by rank (`ItemDeal`), `tide`, or any profile knob; gen reads each on its own, and a level can name more spawn cells, `Level.spawns`, each with a safe zone); what a race is played for (`run: RunRules`: `flag`, `lastStanding`, and `ahead`, what the one standing order in `src/sim/standing.ts` ranks by); its crate (`CrateMix`, with `items` for what its loot boxes deal); what the race camera frames (`camera`: the pack or the leader); how many bouts it fights on a placement when chosen (`bouts`, one if unset); and its scorer. `minPlayers` holds the lobby until enough are seated (bots count); `noWeather` in its profile keeps a weather kind off its levels. Something a race has beyond running the level (the slag, a shrinking arena) is a `RunFeature` in `RUN_FEATURES` (`src/sim/features.ts`) with its own step and kill hooks, its state plain data on the `RunWorld`. tsc then lists the rest: bot `STRATEGIES` and `OBJECTIVES` (`src/brain`), `PASS_BANDS` (`src/game/expectations.ts`), `MODE_EMBLEMS` (`src/render/mode-emblem.ts`). A level shape of its own is a level builder (next). Give it a section in `docs/MODES.md` against its reference game; `tests/conformance/modes.test.ts` holds it to that, to the level it asks for, and to a bot round that plays out. Ask who leads or who is just ahead through `src/sim/standing.ts`, never by reading `level.tide` or heights.
- **Level builder** (a shape or a mode's level): a `BuilderDef` in `BUILDERS` (`src/gen/level/builders/index.ts`) that asks only for kit kinds every set provides; see `src/gen/AGENTS.md` → Set kits and level builders.
- **Brain**: a `BrainDef` in `BRAINS` (`src/brain/registry.ts`) whose `think` reads only the `BrainView` and returns intents; see `src/brain/AGENTS.md`.
- **Weather kind**: add the id to `WEATHER_KINDS` in `src/sim/weather.ts`, then `tsc` lists `WEATHER` and `WEATHER_ART` (`src/render/weather.ts`). Give it a share in `WEATHER_WEIGHTS` (`src/gen/level/weather.ts`), a gate there if it touches the sim, and a sound in `WEATHER_SOUND` (`src/audio/emitters.ts`).

## Game rules

- World: tiles of 16 px. A classic level is `LEVEL_W × LEVEL_H` = 48×27 (768×432, the view); wide and tall levels are bigger and the camera follows (`src/gen/level/profile.ts`). Tiles: `T_SOLID`, `T_ONEWAY` (jump through from below; drop with down + jump), `T_EMPTY`. Spawn left, goal right; protected rects around both can't be built on or bombed; a spawn's shields whoever touches it from props and items for `SHIELD_FRAMES` (5 s) from GO, then nobody (`RunWorld.isSafe`, the one place that decides); the bottom pit kills, and so does leaving off the left or right edge (open air, not a wall: `offMap`).
- Solvability: about 99% of levels can't be finished bare, and about a quarter need two parts (`TWO_PARTS`, `rollChallenges`); the rest need one. Every level is proven finishable with at most two small building props (`MAX_BRIDGES`), and the crate always offers what it still needs (`partsNeeded`, `generateCrate`). What stops a bare run is a gap or wall a part solves, never a sealed level. Placed parts may seal it later; nothing is refused for that, and a sealed level's crate deals a demolition part that clears parts. Always check with `src/sim/reach.ts` (the real controller), never hand-waved jump distances.
- Placement validity lives in `canPlace` (`src/sim/props/transform.ts`). **Attachments** (spikes, ice coat, slime coat) mount flush on a solid face (terrain or placed block); the player's rotation picks the face. They place if at least one cell can mount and permanently keep only those cells (`mountCells`, `landedDef`); everything else needs every cell free of terrain, protected zones and whatever stands there on that frame (`occupiedCells`): movers and set-piece swings pass through placed parts, and a mover's own path only has to keep out of rock and protected zones (`sweptCells`). `placeFaults` is the rule behind both `canPlace` and the red crosses on a refused ghost. Spikes add a hazard strip. Coats change the surface: on floors ice is slippery and slime slow and sticky; on walls ice blocks wall slide/jump and slime makes a sticky cling.
- Scoring: `src/game/scoring.ts`. Everyone finishing or nobody finishing scores nothing.
- Units: world pixels and sim frames (60/s); tile coordinates in `TILE` units; angles in radians, screen space (+y down).

## Hosting

Vercel, Next.js App Router. Server code is limited to small, stateless route handlers and server components in `app/`; no long-lived servers, nothing that costs money at our scale.

Next is one host of the game, not its UI. Another host (a packaged desktop build, a plain static page) mounts it the same way: give `mountGame` an element, and `memoryHistory()` from `src/router.ts` if there's no address bar. `mountGame` adds the screen CSS and fonts if the page lacks them; serving `homeHTML()` and `SCREEN_CSS` in the HTML, as `app/` does, only makes the first paint faster. The music's recorded instruments load from `/samples/` (serve `public/samples/` there, or call `setSampleBase` in `src/audio/music/sampler.ts`); without them the music plays its synth patches. Online play also needs the signaling API at the origin (`src/net/signal-client.ts`): it is peer-to-peer WebRTC with serverless signaling (`docs/NETCODE.md`).

Error and frame-pacing monitoring is Sentry, in the host layer only, so the game stays portable. The game calls `src/telemetry.ts` (`reportError`, `reportEvent`, `reportLog`, `reportMetric`, `addBreadcrumb`, `setTag`, `setContext`), which no-ops until a host installs a reporter; lint bans `@sentry/*` in `src/` and telemetry in `sim/`, `gen/` and `game/`. [docs/TELEMETRY.md](docs/TELEMETRY.md) lists every tag, context, event, log, metric and breadcrumb: add a new one there in the same commit. Event names are fixed strings with variables in `data`, never player names, and nothing goes per frame. Host files: `instrumentation-client.ts` (lazy-loads `app/sentry-browser.ts`), `instrumentation.ts` (server; covers every route handler, traces only the signaling routes), `app/sentry-options.ts` (DSN, privacy settings, trace rates), `app/sentry-filter.ts` (noise filters, page budget, breadcrumb trimming), `app/global-error.tsx` (errors in the React shell itself). A screen that fails to mount is reported by `src/main.ts` (`boundary: 'screen'`) and replaced by the game's error screen; errors thrown later reach the host's global handlers. It only reports from Vercel deploys, so dev, tests and `pnpm shot` send nothing. The release is the commit SHA and the environment is `VERCEL_ENV`.

| Env var | Where | Use |
| --- | --- | --- |
| `SENTRY_AUTH_TOKEN` | Vercel, secret | Source map upload and release creation. Unset: the build skips both and generates no maps. |
| `SENTRY_ORG`, `SENTRY_PROJECT` | Vercel | Slugs for the upload. |
| `VERCEL_GIT_COMMIT_SHA`, `VERCEL_ENV`, `VERCEL_GIT_REPO_OWNER`, `VERCEL_GIT_REPO_SLUG` | Vercel, automatic | Release name, environment, and the commits the release is associated with. |

## Conventions

- TypeScript strict, ES modules. Runtime deps are only `next`, `react`, `react-dom` (for the shell), `client-only`, and `@sentry/nextjs` and `@sentry/browser` (host layer only); the game itself uses none. Don't add runtime dependencies without asking.
- Doc comments explain *why*, on modules and exported functions. Small functions; data plus registries over sprawling `switch`es.
- **Never explain the obvious**, in the game, the docs or your reports. In the game it's a design rule: part of the joy is the unknown, so no sub lines, hints or notes that restate what's on screen or spell out a rule (`docs/DESIGN.md` → Discovery).
- Custom lint and ast-grep rules are welcome where they enforce a rule better than convention. Every rule's error message must steer whoever hits it, usually an agent: say why the rule exists and what to do instead, naming the concrete replacement. Example: `Math.sin differs across browsers and desyncs lockstep. Use dsin from src/core/dmath.ts.`
- Assets: prefer procedural art. The music's acoustic instruments are the exception (owner decision): CC0 recordings built by `pnpm samples`, each with its synth patch as the fallback. Third-party assets only if CC0 or free for commercial use without attribution traps; record each in `public/ASSETS.md` with source URL and license. Keep them small (≤256 px tiles, compressed).
