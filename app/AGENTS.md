# app: Next.js App Router shell

This Next.js version may differ from your training data: read the relevant guide in `node_modules/next/dist/docs/01-app/` before writing route code, and heed deprecation notices.

- **app/ is a host, not the UI.** Every screen (main menu, lobby list, lobby, settings, codex, About, 404, error) lives in `src/` and moves between screens itself (`src/main.ts`, `src/router.ts`), with no Next routing. What's here: server metadata per route, the icons and link-preview files, the stateless `api/` routes, and one shared mount. Don't add React UI; add a screen in `src/` (root `AGENTS.md` → Invariants).
- Every page renders `<Game html={…} />` (`Game.tsx`): the root element, plus `GameHost` → `GameMount` (client, `ssr: false`), which calls `mountGame`. `html` is the screen's markup from `src/ui/screens/markup.ts`, server-rendered so it paints before any script: `/` sends `homeHTML()`, `/lobbies` `lobbiesHTML()` (its frame; the list comes from the client), `/about` `aboutHTML()`, `/r/[room]` the game's dark (after validating the code with `roomFromPath`; a bad one is `notFound()`), `not-found.tsx` the 404 screen, `/codex` and its card permalinks (`codex/[...card]`, which the codex resolves itself) nothing. The layout inlines `SCREEN_CSS` and the fonts. Titles and viewports come from `src/routes.ts` (`routeTitle`, `PAGE_CHROME`, `GAME_CHROME`), which the game also applies on a soft navigation, so a click and a fresh load agree.
- Link previews and icons are file conventions plus `site.ts` (the base URL and shared copy): `favicon.ico`, `icon.svg`, `apple-icon.png`, `public/icons/`, `opengraph-image.jpg` (site) and `r/[room]/opengraph-image.jpg` (invite) are all made by `pnpm brand` from `icon.svg` and the production build; regenerate rather than edit them. `manifest.ts`, `robots.ts` (lobbies stay crawlable for unfurls and carry `noindex` instead) and `api/oembed/route.ts` (stateless oEmbed, discovered through each page's `alternates.types`) complete it. Nothing in `src/` reads any of these.
- Nothing that runs the game may end up in the server bundle: `src/main.ts`, `src/game-client.ts` and `src/codex/main.ts` start with `import 'client-only'`, and the mount loads through `next/dynamic(..., { ssr: false })`. Server code may import only pure modules: `src/routes.ts`, `src/game/room.ts`, `src/ui/screens/markup.ts` and `css.ts`.
- Server code (server components, route handlers) stays small, stateless, and free to run on Vercel.
- `api/net/[op]/route.ts` is signaling and presence for online play; logic and the store are in `api/net/_server/`, shared wire types in `src/net/signal-protocol.ts`. Every Redis key gets a TTL and every command is billed: read `docs/NETCODE.md` → Budget before adding one.
- Sentry is host code: `sentry-browser.ts` and `sentry-options.ts` here, plus `instrumentation*.ts` at the repo root (see Hosting in the root `AGENTS.md`). Route handlers need no setup, because `onRequestError` covers anything they throw. A handler that catches an error and answers 500 itself won't be reported unless it reports explicitly. `global-error.tsx` catches errors in this React shell only; a screen that fails to mount is reported by `src/main.ts`, which shows the game's error screen.
- UI look and copy rules (palette, type, casing, input prompts): `docs/ART.md`.
- React lives only here; `src/` has no React or Next imports.
- `next.config.ts` skips type errors in `next build` because `pnpm check` runs `tsc`.

Verify: `pnpm build` must pass (CI runs it), then `pnpm shot home` (or `lobby`, `codex`) and look at the PNG.
